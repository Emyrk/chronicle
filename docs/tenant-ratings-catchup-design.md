# Tenant ratings: evolving catch-up board

> [!IMPORTANT]
> This document describes an earlier catch-up design. The authoritative replacement
> contract is [`docs/leaderboard-v2/`](leaderboard-v2/README.md).

Status: proposed design, not implemented. This document is the contract for replacing full-generation publication; [the current upload-to-rating walkthrough](instance-upload-ratings.tex) describes today's code, not the target behavior.

## Decision and scope

A tenant's leaderboard is readable while it catches up. It may show incomplete or temporarily stale scores; the page must say so. Do not require a full tenant rebuild or an atomic generation swap before a tenant can see ratings. Normal uploads, reparse, invalidation, deletion, duplicate changes, history discovery, expiry, and rare policy changes feed the **same** durable dirty-work pipeline. Keep the existing materialized, normalized Peak boss and scope scores for now: changing a cohort denominator still repairs affected subjects in bounded pages. No read-time Peak redesign or durable admin chart history is in scope.

Use **one five-minute River dispatcher** and **one `drain-tenant-ratings` job kind per tenant** to consume four typed dirty-key tables. An invocation runs bounded transactions until approximately one minute of elapsed work, then snoozes if work remains or completes if clean. Each daemon may run N rankings workers; River's PostgreSQL job claims and database transactions, not in-process locks, must coordinate them. N workers on D daemons can produce up to N × D concurrent jobs: capacity is an operational setting, not a global per-daemon assumption. An additional historical scan marks the same dirty keys rather than calculating scores itself.

This is **eventual convergence**, not policy-change atomicity. A policy edit may visibly mix old and new scores while a multi-day scan and repair run. Preserve dirty-key revisions and compare-and-swap (CAS) acknowledgments so a newer mutation cannot be permanently lost. A published generation ID, frozen policy manifest, and generation-specific staged score projection are not required in the final design.

### Invariants

1. **Authority lives below ratings.** Canonical logical runs, Renown kill facts, locked parse/time scores, current rating policy, and live player/guild observations are the inputs. A score, denominator, or scope row is replaceable derived state. A duplicate upload contributes at most one canonical run.
2. **Reconciliation is replacement, not addition.** For a key, recalculate all desired rows from authoritative state and atomically replace that key's old rows; disappearance retracts stale rows. It is safe to retry a committed page.
3. **An acknowledged key has been repaired for the revision read.** Source mutations upsert a durable dirty key in the same transaction where feasible. A transaction locks a dirty key, reads current inputs, writes derived state, and CAS-deletes only that key's observed revision. If a later change arrives it remains dirty. Enqueue is an optimization; the periodic dispatcher is the guarantee after missed enqueues or an exit/enqueue race.
4. **Dependencies are explicit.** Run evidence changes mark old and new Mastery subjects and Peak cohorts; Renown facts mark subjects. Peak denominator changes require replay of previously scored and currently observed cohort subjects. Scope scores depend on boss scores and configured roster/weights; disappearing last evidence must retract old scope rows.
5. **Incomplete is visible, not silently complete.** `caught_up` requires source discovery completed for the current scan, all dirty tables empty, no partial Peak page, and no outstanding relevant scan/repair jobs. An empty dirty queue by itself proves nothing about historical coverage. With active uploads this status is momentary, not a promise of permanent freshness.
6. **Tenant isolation survives concurrency.** SQL reads/writes retain tenant and realm authorization; dirty work and cursors are durable and independently retryable. Different tenants can run simultaneously on separate daemons. Shared source/rating locks and revision checks remain database-backed; do not introduce a process-local correctness assumption.

## Repair functions and dependency graph

The word “pure” refers to the *desired-state calculation* `F(authoritative inputs, key, policy, as_of)`. Its worker wrapper performs database locks, CAS acknowledgement and writes. A repair unit is not necessarily an uploaded instance:

| Dirty table / key | Replacement calculation | Downstream dirt / output | Page contract |
| --- | --- | --- | --- |
| `rating_dirty_observation_runs`: tenant + canonical run ID | Resolve current eligible representative. Delete/reinsert this run's player and guild live observations; refresh its source-version stamp. A removed run yields zero observations. | Observation INSERT/DELETE triggers mark exact **old and new** Mastery subject keys and tenant-wide Peak cohort keys. | Current worker handles up to 25 runs/transaction. Preserve ranking-run advisory lock and revision CAS. |
| `rating_dirty_renown_subjects`: tenant + kind + realm + subject + instance + encounter | Count durable player/guild Renown kill facts under current policy for career and rolling period; replace subject-boss Renown rows, then affected raid/scope totals. | Published boss/scope rows for that subject. | Current worker handles up to 25 keys/transaction; never count per raw upload rather than canonical run. |
| `rating_dirty_mastery_subjects`: tenant + kind + realm + subject + full boss/cohort/metric | Replay eligible locked live observations of this exact subject for all-time and 180-day windows, apply current policy, replace Mastery and ranked-Mastery boss rows and affected scopes. | Published boss/scope rows for this subject. | Current worker handles up to 16 keys/transaction. Include old subjects when observation disappears. |
| `rating_dirty_peak_cohorts`: tenant + kind + full boss/cohort/metric, **no realm or subject** | Recompute tenant-wide all-time and period rank-one denominators (max player raw DPS/HPS, min guild duration, including guildless clean kills); page *all* affected current and previously scored subjects, replacing normalized Peak boss/scope rows. | Up to two denominator rows per cohort, then many subject boss/scope rows. | Preserve the durable 16-subject page cursor, keyed by cohort revision; restart/rebase on new dirt. No arbitrary row quota for the River invocation. |

A run's physical observations can be temporarily absent while its replacement transaction is in progress, but readers see only committed state. A Peak cohort spans realms: partitioning by character or upload alone is incorrect. A changed rank one is allowed to leave some already-materialized Peak scores stale until the cohort finishes; the admin/user catching-up indicator must reflect that fact.

### One drain job, not one global lock

`dispatch-tenant-rating-drains` periodically selects the **union of distinct tenant IDs** from the four dirty tables, then enqueues `drain-tenant-ratings{tenant_id}`. Discovery/backfill scanners are producers: they advance their own durable cursors and mark dirty run/subject keys, but a scan with no dirty rows does not keep a drain job spinning. River uniqueness is by kind + tenant args over available/pending/scheduled/running states. It does not depend on a single daemon. Ordinary upload/repair paths may enqueue the same tenant job after committing dirt for lower latency; a failed or deduplicated enqueue cannot lose database work.

The tenant job checks an approximately 60-second *soft* elapsed budget before starting each new bounded transaction. A page in progress may run slightly beyond the budget; apply an explicit per-page/statement timeout so pathological pages cannot occupy a worker indefinitely. The existing River client timeout is 30 minutes; the one-minute budget is an application scheduling choice, not a River timeout. On no pending work it returns success; at the deadline with remaining work it returns `JobSnooze` for a brief delay. Snoozes do not consume River's failure attempts. An exception leaves dirty keys/cursors intact and uses normal retry/error reporting. Once a job completes, a mutation racing its final empty check may have had its enqueue deduplicated against the running job; the next periodic dispatcher must recover it.

**Fairness:** in each cycle attempt at most one bounded transaction from each ready type in order `run → Renown → Mastery → Peak`, then repeat while time remains. Do not drain thousands of runs before giving other types a turn. A Peak transaction handles one cohort page; its saved cursor and revision allow other work/tenants to run before the next page. When the upstream run stage creates new subject/cohort dirt during its own transaction, later stages can pick it up in the next cycle. An empty stage is a cheap no-op. Do not hold one transaction/lock across types or across the one-minute invocation. Stage page sizes are safety bounds independent of the job's *time* limit; they can be tuned after timing production-like workloads. The five-minute dispatcher is the safety net, **not** an additional independent scoring path.

## Historical catch-up and targeted repair

Historical discovery has its own durable `(tenant, source cutoff, after_run_id, scan state)` cursor and enumerates canonical runs in bounded pages. Its only product is dirty run IDs; the same drain worker builds observations and derived rows. Completion means enumeration reached the cutoff **and** related dirty work has drained, not merely that a page returned zero rows. Preserve per-run source-version stamps and daily bounded repair to detect missed intent and source changes. Period expiry marks affected subject/cohort keys daily without deleting career Renown facts. Missing Renown facts may still need the existing bounded fact-repair pass; its inserts trigger the same Renown dirty table, not a separate score writer.

An operator can request a bounded source scan by date, instance, run IDs, or player; it resolves **canonical run IDs** (and the union of previously scored subject keys where required for retraction) before marking work dirty. No selection mode writes ratings directly. Use a stable cursor and fixed scan boundary for resumability, plus the normal mutation path for concurrent new/changed sources. Repeating the scan is safe. A policy-change scan similarly marks affected keys across both source evidence and existing published scores; temporary mixed-policy rows are accepted. Read the current policy when beginning a locked repair page (not from a long-lived job snapshot), and let the scan's later dirty mark/revision CAS force another pass if a policy edit races that page. It must not silently skip a previously scored row after its source disappears. Do not mark one policy version as globally published or prevent board reads while scanning.

## Published data and reader contract

Today `player_tenant_rating_boss_scores`, `guild_tenant_rating_boss_scores`, `player_tenant_rating_scope_scores`, and `guild_tenant_rating_scope_scores` have `generation_id` in their PK/FK and are read through an active-generation filter. Boss keys include tenant/realm/subject/boss/cohort/metric/window; scope keys omit encounter and aggregate raid/portfolio results. `rating_peak_cohort_denominators` also has `generation_id`; `rating_peak_cohort_pages` has a generation fence. The live observation and dirty-key tables are already tenant-scoped and are reused. Target score/denominator PKs are the same *without generation_id*; a tenant has one evolving set of rows under the current policy. Retain `computed_at`, eligible kills and best/form/floor/raw/denominator provenance where present; period rows retain their window start/end. Peak continues to store materialized `score`, `best_raw`, `rank_one_raw` on boss rows and materialized scope scores.

Leaderboard APIs must no longer reject a tenant solely because there is no active generation. Preserve tenant authorization, exact cohort filters, deterministic ordering, full-cohort ranking before display filters, and stable tie-breakers. If an API exposes `generation_id`, explicitly remove or replace that contract in the SDK and frontend and regenerate types. Offset/seek pagination over an evolving sort is **best-effort** across requests: rows may move or repeat/skip as catch-up progresses; do not imply snapshot stability without an actual snapshot. Give the public page a clear `Catching up` state while history or dirty work remains, and show `Caught up` only under the status definition above. Empty because no score evidence exists is distinct from incomplete historical discovery. No requirement to hide incomplete score rows.

## Cutover without supporting old rebuild jobs

The operator reports no rebuilds currently in flight and authorizes killing any old rebuilds at cutover. Do not preserve resumability of an old `building` checkpoint or let an old rebuilding daemon continue writing after the new readers switch. **Still preserve currently active/published score rows:** Octo already has a working board; discarding it would cause avoidable blank pages. Specify an operator cutover that disables old rebuild enqueue/worker/cron/admin controls, drains or cancels old jobs and ensures all daemons run compatible code before switching readers. A rolled-back mixed-version daemon must not write legacy generation tables after the switch.

Because rating score tables are large, **do not put an unbounded copy, full-table rewrite, or index build of historical score rows inside a startup migration**. Introduce generation-free target projection tables and indexes without copying historical rows in startup; copy only each tenant's *active* generation rows into them with an offline/resumable bounded migration job. The copy is a data-transfer bootstrap, not a second scoring algorithm; it preserves existing visible rows. Route readers to the old active projection until that tenant's copy is complete; switch that tenant's reads to the new projection using a durable tenant cutover flag, then allow evolving writes there. Ensure mutations during the copy are captured by durable dirty revisions and replayed after switch; prevent an old generation writer from overwriting copied rows. A tenant with **no** active generation may switch to empty generation-free tables immediately and begin showing partial results as soon as dirty work drains. Once every tenant is switched and no old daemon can run, retire the old-generation projections, rebuild jobs/checkpoints, staging, and generation table with separately reviewed migrations. Retaining old tables temporarily for rollback is acceptable; the **target** has no generations. Preview row counts, indexes, WAL and lock impact before any production-scale cleanup; require approval for a potentially slow startup migration.

The cutover flag and background-copy cursor are rollout mechanics, not permanent generations or a second rating pipeline. A simpler maintenance-window cutover is possible if the operator explicitly accepts a temporary empty board for tenants with active scores; that is **not** the default in this spec.

### Rollout checklist (not automated by migrations)

1. Confirm old `rebuild-tenant-ratings` and `dispatch-rating-scores` jobs are not running, and cancel queued legacy rebuild/old incremental rating jobs before deploying the new workers. Do not run old daemons alongside the cutover; a rollback must not resume writes to the legacy generation tables after readers switch.
2. Migrations 000331–000336 create empty projection/read-state/cursor tables and views, with no historical score copy or full-table rewrite at startup. The five-minute copy dispatcher transfers only each tenant's active published generation in bounded pages; readers continue using those active rows while the tenant is `legacy` or `copying`. Check Admin → Leaderboard → Rating catch-up for each tenant's read state and copy job failures before switching traffic.
3. After a copy reaches `evolving`, the unified drain replays dirt accrued during copying. Tenants with no active generation start directly on partial evolving projections. Historical discovery, dirty-key drain, and pending Peak pages must finish before calling a tenant caught up. No global atomic publication is expected.
4. When a migration changes rating policy or configured bosses, POST `/api/v1/admin/ratings/policy/scan` on each affected tenant's host. The durable six-stage policy scan redirties historical runs and old/new subjects/cohorts in bounded transactions; verify unfinished policy scan stages and backlog return to zero. This is an explicit operator step, not an automatic startup data migration.
5. In staging, exercise more than one daemon and multiple rankings workers, representative switches, deletion, expiry, a changed Peak rank one, scan cancellation/resume, and policy changes while the board is readable. Measure database page times and query plans before raising the per-daemon worker count. Confirm parity of copied active rows before retiring old tables in a separate migration.

## Observability and admin UI

Add a tenant-aware, admin-only current-state snapshot endpoint (tenant-scoped or admin-bypass with authorization), used by Admin → Leaderboard → **Rating catch-up**. Show for each tenant: counts and oldest `changed_at` age for each of four dirty tables; historical scan cursor/cutoff/state; pending Peak page count; River drain state/last successful page, most recent failure, and current backlog status. Show `not started`, `catching up`, `caught up`, and `stalled/error` distinctly, including when scan complete but dirty work remains. Refresh while the page is open and plot sampled backlog counts from those in-memory snapshots. **No durable chart-history table** and no dependency on querying Prometheus from the browser; a reload may reset the local chart. Avoid expensive full-table counts on every page view: use the existing tenant/changed-at indexes, paginate tenants and bound/timeout snapshot queries as needed after measuring.

Instrument all repair stages with bounded-cardinality Prometheus metrics: dirty-key gauges and oldest-dirty-age gauges by key type, running drain jobs, pages/keys processed by type and outcome, page/invocation duration histograms, retries/errors by type, and historical scan progress (pages/keys/unfinished tenants). Do not label by tenant, run, player, guild, cohort or generation. Export database-backed global gauges from each daemon using a collector/periodic refresh; dashboards must **not sum** identical global gauges across replicas (use max or per-instance display). Process-local counters can be summed across replicas. Expose failures without making Prometheus scraping perform slow tenant-wide scans; measure collector time and allow bounded staleness. Monitor oldest dirty age and stalled progress, not only counts (a one-row stuck queue matters). Existing River queue metrics remain complementary.

## Implementation and verification (red → green → refactor)

1. **Red: converge from arbitrary dirt.** Add integration tests that seed canonical runs/facts and assert the same final boss/scope/denominator rows whether repaired in one pass, tiny pages, retried pages, or a different dirty-key ordering. Cover duplicate uploads, representative switches, locked-score arrival after an earlier observation pass, invalidation/clear, deletion of last evidence, guildless Peak rank one, rolling expiry, and a new tenant without an active generation. Ensure a Peak denominator change revisits *old* and *new* subjects. Test transient mixed rows are readable rather than blocked.
2. **Red: multi-daemon race and scan correctness.** Concurrent workers claim the same tenant and different tenants using separate River clients/database connections; verify one active job per tenant, no double acknowledgement, no lost mark when dirt is committed during the final empty check, and durable resume after worker crash midway through a Peak cohort or historical scan. Test cancellation/timeout after a page commit and before it: only whole pages become visible; counters/cursors match. A policy scan racing a repair must eventually revisit the affected key; do not test for an atomic policy switch. Test source discovery empty-queue-not-complete and exact `caught_up` predicate.
3. **Green: schema and workers.** Add new migrations/queries and sqlc generation for generation-free projection and cutover/status state. Adapt the four existing pure calculations and their page-sized transactional wrappers to target the evolving projection; replace four periodic dispatchers with the one five-minute dispatcher and time-bounded tenant drain worker. Reuse fact/observation triggers and revision/CAS; update historical repair/expiry to mark the same keys. Remove the requirement for bootstrap completion or an active generation before writers can repair the partial projection. Keep the current materialized Peak subject-page algorithm.
4. **Green: readers, rollout, observability.** Ship the bounded active-row copier, per-tenant reader cutover, SDK/API/frontend changes, public catching-up indicator, Admin snapshot/chart, and Prometheus collector/instrumentation. Remove all-tenant full rebuild enqueue/control at cutover. Validate score parity for copied tenants and partial-tenant behavior. Keep the old tables read-only until the cutover is verified, then remove obsolete code and schema in separately reviewed migrations.
5. **Refactor and verification.** After tests pass, consolidate duplicate stage-dispatch boilerplate without obscuring typed-key semantics; simplify generation-specific code only after readers and workers no longer depend on it. Run sqlc generation, focused and complete Go tests, race-focused concurrency tests, Go lint, frontend lint/typecheck/build, API/SDK generation and backend build. In staging, test with multiple daemon replicas and `N > 1`, a large tenant, cancellation, policy re-dirty, and a deliberately changing Peak rank one. Track query plans, per-page latency, scrape cost and DB saturation; do not raise global worker concurrency without measuring `N × replicas`. Confirm no production-scale startup migration is shipped without impact review/approval.

**Acceptance:** a newly switched tenant with qualifying configured boss evidence can acquire visible rating rows without a full rebuild; affected Renown/Mastery/Peak boss and scope rows eventually match an independent full recalculation for the same policy/as-of inputs; deletion and invalidation retract obsolete evidence; a newly dirty revision is never acknowledged by an older repair; each page is readable while catching up; a persistent River failure is visible in admin and Prometheus; a second daemon and multiple workers do not lose or duplicate logical work; and no periodic/manual full-generation rebuild is required for ordinary recovery.
